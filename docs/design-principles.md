# 设计原则

本文档是星原 SIS 的**规范性设计约束**。`architecture.md` 描述当前结构，本文档约束以后怎样修改。出现冲突时，应修正实现与文档，而不是增加兼容壳把冲突隐藏起来。

## 1. 目标

项目追求小而完整，而不是层数多。

判断一次设计是否成立，优先看：

1. 一个概念是否只有一个权威实现；
2. 一个用户行为是否只有一条主要生产路径；
3. 依赖方向是否单向、可解释；
4. 测试是否保护当前行为，而不是冻结历史私有 API。

“以后可能有用”“为了保险”“测试还在调用”都不足以让旧实现继续存在。

## 2. 依赖边界

```text
entry
 ├─ CLI
 ├─ Basic UI
 └─ TUI
      │
      ▼
Service / Auth
      │
      ▼
Repository
      │
      ▼
SQLite
```

- UI 不写 SQL；
- Repository 不依赖 UI；
- 业务校验进入 Service / Schema；
- SQL 进入 Repository；
- 跨层需求沿现有方向扩展，不通过反向 import 或旁路实现。

## 3. 单一权威实现

| 概念 | 权威实现 |
| --- | --- |
| 登录后门户 | `tui/app.py` + `tui/portal.py` |
| 工作台状态 | `tui/workspace/state.py` |
| 键鼠事件意图 | `tui/workspace/events.py` |
| 档案共享 target / 绘制 / 滚动 | `tui/workspace/inspector.py` |
| 学生档案结构 | `tui/workspace/student_inspector.py` |
| 其他实体档案结构 | `tui/workspace/detail.py` |
| 单字段输入与完整事务表单 | `tui/workspace/forms.py` |
| 字段展示值 | `tui/workspace/presentation.py` |
| 工作台几何与可见区 | `tui/layout.py` |
| 文本输入状态 | `tui/text_edit.py::TextBuffer` |
| UI 颜色语义 | `tui/tokens.py` |
| 当前数据库结构 | `database.py::SCHEMA` |
| 业务写操作 | `service.py` |
| SQL 持久化 | `repository.py` |

出现第二套实现时，默认动作是合并或删除，而不是增加同步代码。

## 4. 焦点与编辑能力分离

档案字段必须区分：

```text
focusable
editable
```

`focusable` 决定字段是否属于档案空间几何；`editable` 决定 Enter 是否可以开启修改。

因此：

- 只读字段可以被方向键选中；
- 只读字段不能因为“不可编辑”而从导航图消失；
- 事件层不能通过 `edit-field:*` 同时表达“这是焦点 target”和“这是写操作”；
- 浏览 target 使用稳定字段身份，当前约定为 `field-target:<key>`；
- 字段编辑是这个 target 的临时子状态，不建立第二套导航坐标。

这是所有记录页的通用规则，不为学生页面单独维护例外。

## 5. 已有记录没有编辑页面

已有记录的修改必须发生在当前档案字段上：

```text
field-target
   │ Enter
   ▼
字段局部输入 / 选项
   │ Enter
   ▼
校验 → Service → Repository → 回到原 target
```

必须遵守：

- 文本 / 数字 / 日期字段确认后立即保存；
- 枚举 / 外键选项确认后立即保存；
- Esc 取消当前字段；
- 字段修改期间没有记录级保存按钮；
- 不把全部字段复制成第二套 `form.position` 顺序；
- 一个字段修改不能无故拥有其他字段的临时值；
- 明确存在一致性约束的复合字段可以拥有一个小字段组并原子提交。

学生 `family + branch` 是当前明确的复合字段。

新建、删除确认、密码重置、导入 / 导出、seed 是完整事务，可以使用独立表单 / 确认面板；它们不属于已有记录字段编辑。

## 6. 导航只有一条主路径

同一个方向意图不能按设备或页面分叉出多套实现。

聚焦档案时：

```text
键盘方向键 ─┐
鼠标滚轮 ───┼→ 统一导航入口 → 当前 inspector 几何
其他等价输入 ┘
```

`events.py` 不能硬编码“学生物种”“元素亲和”等页面字段。学生与普通实体的差异应由各自生成的真实 `Line` 几何表达。

普通档案是一列；学生档案可以有复合行。差异属于内容几何，不属于事件状态机。

## 7. 数据事实不等于业务规则

演示数据事实不能自动升级成长期业务限制。

例如：

- 当前 seed 没有某物种，不意味着系统禁止该物种；
- 某角色年龄很大，不意味着学生年龄存在门禁；
- 某批角色只有生日月日，不意味着出生资料必须完整。

只有需求明确要求长期约束，并且它属于系统业务语义时，才进入 Schema / Service。

## 8. 新抽象的准入条件

新增模块、helper、wrapper、adapter、manager 前，至少应满足一项：

- 表达稳定、可命名的领域或交互概念；
- 被两个以上当前生产路径以同一语义复用；
- 切断真实依赖耦合；
- 拥有独立生命周期或状态模型。

这些理由单独出现时不成立：

- “以后可能复用”；
- “看起来更企业级”；
- “为了兼容旧私有函数”；
- “测试还在调用”；
- “只有一行转发，留着更安全”。

没有新增语义的薄 wrapper 应删除。

## 9. 兼容与迁移

当前项目没有已发布数据库版本兼容承诺。`initialize_database()` 只创建当前 schema，不隐式修补旧数据库。

未来若需要迁移，应：

1. 明确起始 / 目标版本；
2. 使用显式迁移步骤；
3. 针对真实版本边界测试；
4. 迁移失败必须可见；
5. 明确旧迁移何时可删除。

源码目录、私有函数、内部 action 名称、颜色 token 同样默认不承诺历史兼容。

## 10. 测试策略

测试保护行为，不保护旧实现形状。

- 不因为旧测试直接调用私有 helper 而恢复废弃入口；
- 交互回归优先走真实 `events.interact()` 路径；
- helper 测试可以补充算法边界，但不能代替端到端事件测试；
- seed 测试不绑定偶然学号或班级位置；
- 已有记录编辑测试必须验证“原档案 Enter → 修改 → Enter 保存 / Esc 取消”；
- 必须验证字段编辑不存在记录级保存按钮；
- 必须验证只读字段仍在焦点图中；
- 鼠标 / 键盘等价行为应比较真实最终状态，而不是分别测两个 helper。

## 11. CI 原则

优先运行与修改范围直接相关的测试。

只有跨模块架构调整、数据库 / Service / Repository 主链修改、核心交互状态机修改，或定向测试暴露出系统性不确定性时，才值得跑完整 CI。纯文档、纯数据和局部低风险修改不应机械触发完整回归。

## 12. 文档分工

- `README.md`：外部读者先看，说明项目、运行方式与主要交互；
- `docs/architecture.md`：当前模块边界与依赖；
- `docs/ui-design.md`：视觉 / 焦点 / 导航语义；
- `docs/data-model.md`：实体与字段；
- `docs/record-presentation.md`：档案展示值与字段会话；
- `docs/demo-data-sources.md`：演示角色资料；
- `docs/design-principles.md`：修改代码必须遵守的结构性约束。

文档只描述当前真实设计，不保留 merge 冲突、废弃路径或历史兼容说明。

## 13. 修改前检查

结构性修改合并前应回答：

1. 这是不是已有概念？为什么不能扩展权威实现？
2. 是否产生第二条生产路径？
3. 焦点与编辑能力是否被错误绑定？
4. 同一个输入意图是否因页面 / 设备走了不同逻辑？
5. 是否为了测试或旧私有 API 保留无语义 wrapper？
6. 是否把当前演示数据事实写成长期业务限制？
7. 文档是否描述当前真实实现？
