# 设计原则

本文档是星原 SIS 的**规范性设计约束**。`architecture.md` 描述当前结构，本文档约束结构以后如何变化。两者冲突时，应先修正实现与架构文档，而不是增加兼容壳把冲突隐藏起来。

## 1. 目标

项目追求的是小而完整的系统，而不是层数多的系统。判断一次设计是否成立，优先看四件事：

1. 一个概念是否只有一个权威实现；
2. 依赖方向是否单向、可解释；
3. 删除旧实现后是否仍有生产路径依赖它；
4. 测试是否验证当前行为，而不是迫使生产代码保存历史形状。

“以后可能有用”“为了保险”“测试还在调它”都不足以让一段代码继续存在。

## 2. 当前依赖边界

```text
entry
 ├─ CLI
 ├─ Basic UI
 └─ TUI
      │
      ▼
Service / Auth
      │
      ▼
Repository
      │
      ▼
SQLite
```

约束如下：

- CLI、Basic UI、TUI 可以有不同交互模型，但不得各自实现业务规则。
- 业务校验进入 `service.py` / `schema.py`，SQL 进入 `repository.py`。
- `database.py` 只负责当前 schema、连接与事务，不承担历史版本适配。
- UI 渲染代码不得写数据库；Repository 不依赖任何 UI。
- 一个跨层需求必须沿现有依赖方向扩展，不能通过反向 import 或旁路解决。

## 4. 数据事实不等于业务规则

演示数据中的事实、当前产品选择和长期业务不变量必须区分。

例如：

- “当前 seed 没有兔科角色”是数据事实，不意味着系统禁止兔科；
- “某批角色年龄在某范围”是数据特征，不意味着学生年龄存在业务门禁；
- “当前 UI 只有暗色主题”是实现状态，不意味着主题层必须拒绝其他主题。

只有在需求明确要求长期约束，并且该约束属于系统业务语义时，才可以进入 schema/service 的校验。一次性数据整理不得自动升级成长期 guard、README 警告或架构原则。

## 5. 新抽象的准入条件

新增模块、helper、wrapper、adapter、manager 或中间层前，至少应满足下面一项，并且不能违反其他项：

- 它表达一个稳定、可命名的领域或交互概念；
- 它被两个以上**当前生产路径**以同一语义复用；
- 它切断了真实的依赖耦合，并使依赖方向更清晰；
- 它拥有独立生命周期或状态模型，放在调用者内部会造成职责混杂。

以下理由单独出现时不构成抽象依据：

- “以后可能复用”；
- “这样看起来更企业级”；
- “为了兼容以前的私有函数名”；
- “测试直接调用旧 helper”；
- “只有一行转发，但留着更安全”。

薄 wrapper 若没有新增语义、边界或策略，应直接删除，让调用方使用真实抽象。

## 6. 兼容与迁移策略

当前项目没有已发布的数据库版本兼容承诺，因此**启动路径不做隐式旧 schema 迁移**。`initialize_database()` 只创建当前 schema。

如果未来确实需要版本迁移，必须作为明确的产品能力引入，而不是在 `initialize_database()` 中逐步堆叠 `if column not exists`：

1. 明确支持的起始版本和目标版本；
2. 使用独立、可识别的迁移步骤；
3. 有针对真实版本边界的迁移测试；
4. 迁移失败必须可见，不能静默回退；
5. 明确何时可以删除旧迁移。

同理，源码目录、私有函数、颜色 token 和内部 UI 结构默认不提供历史兼容别名。若外部 API 真正形成兼容承诺，应在文档中显式列出其稳定范围。

## 7. UI 设计约束

### 7.1 导航

登录后的 TUI 只有一条首页路径：

```text
app.run → app._portal_home → portal.frame
```

测试直接验证这条路径。不得为了保留旧布局测试重新增加另一套 `home_frame`、旧 labels 菜单或 `legacy_actions`。

**已有记录不存在“编辑页面”或“整条记录编辑模式”。** 档案在浏览和修改前后使用同一份 renderer、同一条 target 顺序和同一个浏览焦点 `detail_selected`：

```text
档案 target
   │ Enter
   ▼
当前字段输入 / 选项子状态
   │ Enter
   ▼
校验 → Service 保存 → 回到同一档案
```

字段编辑必须遵守：

- Enter 在当前可编辑字段上进入该字段的输入子状态；文本或选项再次 Enter 后立即校验并保存。
- Esc 取消当前字段的本次修改，不影响其他字段，也不产生整条记录草稿。
- 字段编辑期间不显示“保存”按钮；保存不是档案中的第二个可导航目标。
- 选项列表只是当前字段的子状态，不能替换档案的整体方向键导航模型。
- 修改单个字段时不得把全部字段重新变成一套 `form.position` 导航序列。
- 有一致性约束的复合字段可以进行多步选择并原子提交。当前学生物种的 `family + branch` 属于这种情况：选族系后继续选支系，最终一次保存。
- 新建记录仍然天然是多字段操作，可以使用完整表单和显式“保存”；删除、seed 等破坏性 / 批量操作可以使用显式“确认”。这与已有记录的字段编辑不是同一种交互。

### 7.3 颜色

`tui/tokens.py` 只保存语义 token：`text-*`、`surface-*`、`border-*` 以及明确标注为 decoration 的颜色。不得保留 `_ACCENT`、`_DIM`、`_SELECTED` 之类第二套历史命名。

组件可以组合语义 token 形成组件样式，例如“默认页面表面 = surface-default + text-primary”，但这种组合只属于组件，不得重新冒充新的全局 token。

### 7.4 文本输入

`TextBuffer` 是文本值、光标和可见窗口的唯一模型。终端输入层直接把 `TextBuffer` 传给绘制函数，不再通过“chars + cursor → 临时 TextBuffer”的兼容 wrapper 往返转换。

## 8. 测试策略

测试的职责是保护当前公开行为与关键内部契约，不是冻结历史实现。

必须遵守：

- 生产代码不能因为“测试还在调用”而保留废弃入口；应修改测试。
- 布局测试必须针对当前 renderer，例如 portal 或 student inspector。
- seed 是演示数据，可以变化；测试不得依赖“某固定学号永远对应某角色”这类偶然事实。
- 需要样本时，优先由当前 seed 动态取得，或在测试中创建最小 fixture。
- 字段编辑测试应验证“原档案内 Enter → 修改 → Enter 保存 / Esc 取消”，以及字段编辑期间不存在独立保存按钮；不得重新要求整条记录编辑表单。
- 可以测试稳定私有算法（例如 terminal cell clipping），但不能据此要求生产路径保留已经废弃的 façade。
- 回归测试应描述行为，例如“焦点切换后选择仍可见”，而不是描述旧函数名。

## 9. 文档分工

- `README.md`：用户能做什么、如何运行。
- `docs/architecture.md`：当前代码由哪些部分组成、依赖如何流动。
- `docs/ui-design.md`：视觉和交互语义。
- `docs/data-model.md`：数据关系与字段模型。
- `docs/design-principles.md`：修改代码时必须遵守的结构性约束。
- `docs/demo-data-sources.md`：演示角色数据来源，不承担业务规则。

不要把一次性实现细节写成永久产品承诺。规范文档只记录真正希望未来继续成立的约束。

## 10. 修改前检查

一次结构性修改在合并前应回答：

1. 这是不是已有概念？如果是，为什么不能扩展现有实现？
2. 是否产生了第二条生产路径？
3. 是否把当前数据事实误写成了长期业务限制？
4. 是否为了测试、旧目录或旧数据库保留了转发层？
5. 新 helper 是否真的拥有语义，还是只包了一次函数调用？
6. 删除旧代码后，是否有测试失败只是因为测试绑定了实现细节？
7. 文档描述的是当前真实架构，还是已经不存在的历史？
8. 已有记录的修改是否仍然在原档案 target 上完成，而不是悄悄引入第二套编辑焦点？

如果答案暴露出第二实现、猜测性 guard 或无语义 wrapper，应先删除这些接缝，再继续增加功能。

## 11. 例外

任何违反本文规则的兼容层或重复实现都必须是**显式例外**：说明用户价值、支持范围、所有者和删除条件。没有这些信息的“先留着”不算设计决策。
